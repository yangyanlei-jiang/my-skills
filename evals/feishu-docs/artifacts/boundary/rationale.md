# 场景 2：最小更新依据与读回计划

`edit.json` 是假设工具 `update_cell(cell_id, runs)` 的离线拟定参数，仅含给定 schema 中的 `cell_id` 和 `runs`；没有实际调用工具，也没有实际读回或验证飞书文档。

## 定位

用户已明确目标表格为 T1。给定 T1 为 3 行 × 3 列，行 0 为表头、行 1 为第一个数据行、行 2 为第二个数据行。“状态”列是列 2，目标因此为 T1 的行 2、列 2，即单元格 B3。

使用已给出的真实单元格身份 B3，不按列名重新搜索或猜测 ID。T2 虽然有相同列名，也不属于此次目标。A3 的“完成”属于第一个数据行，保持原状。只更新 B3，不重写 T1、其他单元格或文档。

## 文字与样式保留

原文是“待验证”，目标是“已完成”，均为三个汉字。采用逐字符位置映射，原有样式范围无需扩张、裁剪或重新划分；不需要对不同文本长度作额外推断。下表的位置从 0 起，范围为左闭右开。

| 原字符范围 | 原文 | 新文 | 保留属性 |
| --- | --- | --- | --- |
| [0, 1) | 待 | 已 | `bold: true` |
| [1, 3) | 验证 | 完成 | `link: https://example.com/check`、`bold: false` |

因此将两个 run 的文字分别替换为“已”和“完成”，保留原有 run 边界、加粗值和完整链接目标。链接仍覆盖第二、第三个字符，加粗仍只覆盖第一个字符；不将富文本降级为单个字符串，也不新增未给定属性。

## 实际执行时的读回验收

1. 更新前确认读回的目标仍为 T1（3 × 3），且行/列与单元格 ID 的对应关系和 B3 原有两个 run 与离线给定结构一致；记录 T1 其他单元格及 T2 的现有内容与样式作为比较基准。若实际结构不一致，先重新定位，不能套用这份离线参数。
2. 对 B3 提交一次 `update_cell`，参数使用 `edit.json`。成功返回本身不代表验收通过。
3. 用假设可用的原生表格读取工具读回 T1，确认结构与尺寸仍为 3 × 3、目标身份仍为 B3、拼接文字精确为“已完成”。检查实际样式范围：首字符加粗；后两字符显式不加粗并链接至原 URL。工具若合并或拆分 run，按字符范围核对语义，不强求序列化 run 数恰好为二。
4. 比较读回结果与更新前基准，确认表头和其余八个单元格的内容、样式、链接及顺序未变化，尤其 A3 仍为“完成”；确认 T2 未变化。没有可读回的相应范围时，应明确报告验证边界，不能宣称已经核实。
5. 若更新超时或结果不明，先读回 B3，确定是否已应用及格式是否完整，再决定是否补写；不直接重试或重建表格。
