Git 作者归属说明代码经过本人提交，不能证明每行都是本人从零手写。看新增行、主动修改和反复出现的结构；基类、旧代码、工具格式化与协作内容单独归类。提交定位、原路径和私有代码证据保留在本机工作资料中，不随技能发布。模板均为抽象改写。

## 代码风格与规范

直接证据较强的特征：

- 专门的格式化提交将单行数组改为 `[ 'key' => $value ]`，多行关联数组对齐 `=>`；这是比“现有代码恰好如此”更明确的偏好。
- 新增代码普遍使用 PascalCase 类、camelCase 方法/变量、snake_case 字段；模型名称与业务类冲突时用 `as XxxModel` / `as XxxBusiness`。
- 中文注释以资格判断、版本兼容、时间定义、批量查询和重试不变量为中心；PHPDoc 用于业务职责与参数语义。
- 条件不满足直接返回默认结果或跳过元素；成功路径在尾部返回，减少深层嵌套。
- 关系方法、策略、缓存和较新内部服务出现 `int`、`bool`、`array`、nullable、明确返回值和类型属性。本人也维护未声明类型的旧入口，不能将“全量强类型化”归为一致习惯。

保持弹性：短数组内空格、`(int)$value` 与 `(int) $value`、`!foo()` 与 `! foo()`、单双引号、单行返回数组键序和尾逗号存在差异。formatter 和当前文件优先，默认数组偏好仅用于缺少当地规范的新代码。

## 架构与设计模式

项目具有 Lumen 9、Composer PSR-4、四空格/LF 的公共环境；仓库规范标明 PHP 8.1，而 Composer 的版本约束较宽，不能据此把任意 PHP 新语法用于目标部署。

Controller → Version → Business → Model/Cache 是项目兼容结构，不是个人风格必须在任何框架重造的架构。本人新增/修改的业务类进一步体现：

- 使用 `make()` 与容器解析复用项目基类；有 SingletonResolvable Trait，但不是每个类都必须成为单例。
- 复杂模块按策略、存储、格式化、业务编排拆分；简单查询也存在直接放在 Business 或 Model 的写法，不能要求“每个模型必有 Repository”。
- Facade、静态 helper、容器获取与构造注入共存。已有简单模块复用 helper，独立或可替换依赖采用注入；不要求将全部旧代码迁为某一种设计模式。
- 新增 Model 相对轻量，沿用 BaseModel/BaseReadWriteModel，显式 table、guarded 或 casts。连接、分表与读写分离是实际数据行为，不能仅视为样式。

## 技术栈与查询特征

- Eloquent 链式查询常先过滤和选择必要字段，再 `get`、`pluck`、`keyBy` 或转数组；也使用 Query Builder、join、窗口函数及绑定合并处理具体性能问题。
- 可观测的改动包括：合并重复查询到 join、批量获取关联状态和数量、批量候选之后显式组装客户端结果。
- Carbon/CarbonImmutable 用于自然日边界；ClientInfo、配置、语言/地区 helper 为当前上下文来源。队列及长期对象需使用明确传入的上下文，不能假定请求静态变量仍有效。
- PHP 的 `??`、`?->`、短闭包和 nullable 返回被使用；选择简短且能保留语义的表达方式，不以语法糖替代边界检查。

## 核心业务范式与错误机制

1. 接口兼容：常见 Version 方法显式返回 `data/code/msg`，Controller 调用 jsonResponse。项目历史还存在不同输入包装和 JSON 返回路径；先核对具体调用链。
2. 条件前置：无资格、无配置、空集合和旧版本分支尽早退出；不把例子的用户分类、金额或时间常量写入风格规则。
3. 可选降级，必要失败：展示模块存在默认结果和缓存/日志降级；本人也主动移除了支付执行中 catch 后返回 false 的写法，使必要异常能继续向上层传播。二者必须分开。
4. 结构化且克制的日志：有提交主动移除大量正常守卫和成功路径 info 日志，同时保留频控、重复处理和异常诊断。日志语言、上下文键风格不完全统一。
5. 有状态操作关注重放：较新模块使用同连接事务、锁后复查、幂等记录、缓存参数 fingerprint、Lua 原子提交及锁 token 检查。这是复杂操作下的条件性范式，不要求纯读接口也加入事务/锁。
6. 分段发布：版本、实验、配置映射、地域/语言分支频繁出现；保持现有契约与分阶段兼容，只有任务明确要求时才清理过时分支。
