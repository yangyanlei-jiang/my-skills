# Markdown 生成与批量转换

先把内容与可表达的格式写进 `.md`，再发布和补齐。仅生成 Markdown 的任务无需浏览器或飞书账号。补齐项说明放在正文之外，不把操作清单混入正式文档。

## 选择目标格式

- 已明确写入工具：按该工具的 Markdown 契约生成，包括它真正支持的飞书扩展。
- 未明确或离线：先生成基础 Markdown，并给出必要的原生补齐项。不要假设所有飞书工具、文件导入和编辑器快捷键使用同一套方言。
- 工具支持 Markdown 内嵌 XML 扩展时，可以在生成阶段实现更多原生格式；这属于该工具的转换语法，不能推定普通 Markdown 阅读器或导入器也支持。

## 基础正文在生成阶段完成

使用连续的标题层级、正文段落、有序/无序列表、`**重点**`、行内代码、链接和带语言的代码围栏。块之间留必要空行，不加装饰性空白或手工目录。

独立 `.md` 可以以 `# 文档名称` 开头。若写入接口提供标题字段，提取名称到该字段，并从正文移除重复首行；以具体导入契约为准。

表格完整写出表头与数据，指定加粗、链接等富文本在单元格中表达：

```markdown
| **项目** | **负责人** | **状态** |
| --- | --- | --- |
| 幂等校验 | 小林 | **完成** |
| 灰度验证 | 小周 | 待验证 |
```

单元格中的字面管道符按方言转义。合并单元格、多个块或复杂布局只有目标扩展明确支持时才直接生成；否则保留完整数据并列出所需补齐。不要为基础表格默认规划九次单元格输入。

全部表格采用 [原生格式中的 2.2 样式](native-format.md)：浅灰、加粗居中表头，正文左对齐、自然换行和细边框；接口入参、返回字段、基本信息及其他表格统一铺满正文可用宽度，左右边界对齐，少量数据也不生成短表。目标支持对应 XML 扩展且宽度已知时直接在 `.md` 表达每张表的样式与列宽；普通管道语法不具备的样式/全宽逐表列入局部补齐项，不使用猜测的 CSS，也不为了样式或宽度重建整张表。

SQL、JSON、Python 等代码围栏在 `.md` 中直接标注语言；保持代码原文，不把代码中的符号按正文转义。

## 飞书扩展：支持时直接生成

飞书官方 CLI 的 [Markdown 参考](https://github.com/larksuite/cli/blob/main/skills/lark-doc/references/lark-doc-md.md) 明确允许 Markdown 使用其定义的 XML 扩展；具体标签见 [XML 参考](https://github.com/larksuite/cli/blob/main/skills/lark-doc/references/lark-doc-xml.md)。其他工具须检查自己的契约。

例如，目标链路明确支持这些标签时：

```markdown
计划上线日期：<u>2026-10-15</u>。

<callout emoji="⚠️" background-color="light-yellow">
<p>回调重试可能导致重复记账。</p>
</callout>
```

这两个格式已经在生成阶段表达，成功转换后无需浏览器重做。不要转义所需扩展标签，也不要放进代码围栏使它变成源码展示。普通正文中的字面尖括号、特殊字符按当前方言转义。

仅支持基础 Markdown 的链路则保留日期和风险文字，并在独立补齐清单中记录“日期加下划线”“风险段落转高亮块”。引用块只能作为风险内容的中间表示，不能算作已经完成的 callout。

任务、公式、图表、提及、合并表格等其他扩展按实际需要读取当前工具文档，避免把旧版本标签套入新工具。只有无法通过当前 Markdown 链路表达的原生项，才交给后续工具或浏览器补齐。

## 批量写入与集中验收

1. 本地检查 Markdown 的内容、层级、表格数据、代码与需要补齐的原生项。
2. 使用已授权的 MCP、CLI、API 转换或 `.md` 文件导入，批量创建或更新。大文档按真实限制分批。
3. 内容通过结构化参数、文件或 stdin 传递，保留真实换行和反斜杠；不要把多行内容拼进会展开变量或反引号的 shell 字符串。CLI 的参数和相对路径限制由当前 `--help` 决定，不冻结旧命令。
4. 检查返回的告警及实际转换结果；只有缺失的原生项进入局部补齐。已有富文本表格不要整表重建。
5. 最后集中检查一次。转换错误或补齐失败先核实局部结果再修正，不盲目重复发布或反复试排版。

普通 `.md` 文件上传和“转换为可编辑飞书文档”是不同操作。云端交付要确认目标对象确为原生文档，而不是仅能下载的 Markdown 文件。
